# 记忆架构提案（v2）

> 目标：**存储可以无限长，读进上下文的那一小块有上限。**
> 她可以忘记、可以记错、可以纠正、可以改对过去的理解，但**不能抹掉真实发生过的历史**。

## 一、现在的样子（问题在哪）

```
life/memory.md        一个文件，一行一条，行尾 [src:x] [hN]
life/memory.log       写入日志（只有 add / supersede 两种）
上限 10000 字         超过就拒绝写入
```

四个问题：

1. **容量和注意力混在一起**：写不进去是因为"上下文读不下"，不是"记不住"。
2. **命中次数只影响排序**，不影响"还记不记得"，所以遗忘是不存在的。
3. **删除是真的删除**：`drop` 会把那条从文件里拿掉，历史随之消失。
4. **纠错只能靠"再写一条"**，新旧两条并存，谁对谁错没有标记。

## 二、要分开的三件事

| 层 | 是什么 | 容量 | 谁在动 |
|---|---|---|---|
| **存储层** | 一条经历本身，不可变 | 无上限（按年分片） | 只追加 |
| **索引层** | 怎么找到它（时间/人物/关键词/强度） | 无上限 | 派生，可重建 |
| **上下文层** | 这次对话读进去多少 | 有上限（8–10K 字） | 每次重算 |

**容量问题在上下文层解决，不在存储层解决。**

## 三、存储：一条记忆是一个不可变记录

```
life/mem/
  2026-10.md          按月分片（人也能直接读）
  2026-11.md
index.jsonl           每条一行：id / 时间 / 分片 / 关键词 / 强度 / 上次被想起
events.jsonl          只追加：created / recalled / corrected / reinterpreted
```

一条记录的形状（md 里用标题分隔，index 里用 JSON）：

```
## m-20261115-0042
2026-11-15 他说不想维持社交关系，只想一个人宅着听歌打游戏。
  src: chat#msg-8812          ← 指向原始对话，可回溯
  w: 5                        ← 内容重要性
  seen: 7 次  (最近 2 天前)    ← 被想起的次数与时间
  rev: 1                      ← 修订代次
```

**不删除。** 纠错是新增一代 `rev`，旧代保留；重新理解是另一层注解，不覆盖原文。

## 四、遗忘：不是删除，是"想不起来"

用 ACT-R 那套激活度，不发明新东西：

```
activation = ln( Σ (现在 - 第 j 次想起的时间)^-0.5 ) + w × 0.3
```

含义：

- **被想起一次 → 激活度上升**（间隔越近，涨得越多）
- **长期不被想起 → 自然衰减**（衰减是连续的，不是到期删除）
- **线索匹配（关键词/人物/时间）→ 临时把匹配项拉高**（这就是"忽然想起"）

**读进上下文的，是"当前激活度最高的那几条 + 与本次话题相关的几条"。** 其余留在盘上。

于是：

```
旧的、没再被想起的  → 沉下去（她真的想不起来）
但还在盘上          → 一旦被关键词/日记/他自己的话勾到，能重新浮起来
```

**这就是自然遗忘：可提取性变化，而不是数据消失。**

## 五、纠错与重新理解

三种动作，都不删原文：

| 动作 | 语义 | 记录 |
|---|---|---|
| **correct** | "我记错了，实际是 X" | 新代 rev+1，旧代留档，`events` 记 corrected |
| **reinterpret** | "同一件事，我现在不这么看了" | 加一层注解，原文与旧解释都保留 |
| **retract** | "这条不该被当成事实" | 标 `retracted`，不再进上下文，但记录还在 |

**她读到的永远是"当前的解释"，但索引里能查到"她以前怎么理解"。**

## 六、记忆写入：分级 + 证据（已做一半）

现在已有的：`[src:chat|web|infer]` + 当轮原话比对。

要补的：

- `src:chat` 必须带**原始消息 id**，能点回 chat-archive（可回溯）
- `src:infer` 永远单独渲染成「（我推的）」，**不允许升格成 chat**
- 写入时若与已有记忆冲突（同一人同一事），**不覆盖**，标 `conflict` 等后续澄清

## 七、容量：上限从存储挪到上下文

```
存储上限      无（按月分片，一年约 20 个文件）
上下文上限    8–10K 字（现在是 10K，维持即可）
```

**写不进去的问题因此消失。** 需要限制的只有"这次读多少"，而那是每次都能重算的。

## 八、读的时候怎么选（三段）

```
① 核心       w ≥ 4 且最近 90 天被动过     → 最多 20 条（她的人格底座）
② 相关       与本次输入共享关键词/实体     → 最多 12 条
③ 最新       最近 7 天                     → 最多 10 条
```

**其余靠 `recall`（她主动问）按需翻。** 她已经会用这个动作了。

## 九、迁移（不动现有内容）

1. 把 `memory.md` 按日期拆进 `life/mem/YYYY-MM.md`，**逐字搬运，不重写**
2. 生成 `index.jsonl`：id、时间、关键词、w、`[hN]` → `seen`
3. `memory.log` 转成 `events.jsonl` 的第一批 `created`
4. 旧的 `[hN]` 全部保留，映射成 seen 次数
5. 切换读路径：soul 只读 index + 命中的分片，不再整文件读

**风险点**：拆分脚本必须先备份、可回滚；读路径切换要保留旧路径开关。

## 十、需要她同意的事

按现有规矩，下面这些都得先问她，**而且是说后果，不是贴代码**：

- 记忆不再"删"，只有"想不起来"和"我记错了" —— 她还能不能要求彻底抹掉某条？（**「删除权」是她现在的权利之一，砍掉要她点头**）
- 她自己写的东西，以后会带"（我推的）"标记
- 记忆会按月分文件，她翻的时候路径变了

## 十一、还开放的问题

1. **删除权**：她原有"要求删掉某句话"的权利。这套架构默认不删——**冲突，需要她裁决**。
2. **重新理解**要不要进上下文？还是只在她主动回忆时给？
3. 关键词从哪来：分词？她自己标？还是模型生成？**生成又引入幻觉**。
4. 分片到多细：按月 / 按 500 条 / 按主题。
